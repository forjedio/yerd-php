# Windows builds

This document explains how yerd-php produces the Windows PHP artifact and why it
works differently from the macOS and Linux artifacts. Read it before touching any
of the Windows code paths.

## TL;DR

On macOS and Linux we build a static single-file PHP with static-php-cli. On
Windows we do not. We repackage the official non-thread-safe (NTS) build from
windows.php.net into a directory bundle. The bundle contains `php.exe`,
`php-cgi.exe`, `php8.dll`, an `ext/` directory of
extension DLLs, the support DLLs (libpq, OpenSSL, and so on), a generated
`php.ini`, and a CA certificate bundle.

Build one locally with:

```bash
scripts/build-local.sh 8.4 windows
```

## Why not static-php-cli on Windows

static-php-cli builds a genuinely static `php.exe` on Windows, and we spent real
time getting it to compile (it needs the VS BuildTools detection fix, System32
bsdtar ahead of the Cygwin tar on PATH, vswhere on PATH, and
`NoDefaultCurrentDirectoryInExePath` cleared). It builds. The problem is that a
static Windows PHP is the wrong shape for yerd, for two reasons that cannot be
worked around:

1. **No dynamic extension loading.** A static `php.exe` exports no PHP API for a
   `.dll` to link against, so it cannot load extensions at runtime. That kills
   yerd-php-ext: `yerd-dump.dll` could never load into it, and the Dumps feature
   would not exist on Windows.

2. **No pgsql.** static-php-cli builds libpq as a DLL on Windows (the `libpq.lib`
   it produces is a 37 KB import stub, not a static library). Linking `pgsql` or
   `pdo_pgsql` therefore makes `php.exe` depend on `libpq.dll`, which the static
   build then strips, so the binary fails to start with STATUS_DLL_NOT_FOUND.
   Postgres support is not optional for yerd, so this alone rules the static
   build out.

Both of these are solved by a normal DLL-based PHP. That is what the official
Windows builds are, and it is how native Windows PHP is normally distributed. So
we use it too.

## What we ship instead

We download the official `php-<version>-nts-Win32-<vs>-x64.zip` from
windows.php.net, unpack it, enable the extensions yerd wants, add the PECL
extensions the official build does not include, drop in a CA bundle, and archive
the whole tree.

The result is one artifact per (version, revision):

```
php-<version>-<revision>-bundle-windows-x86_64.tar.gz
```

which unpacks to a directory:

```
php.exe            CLI
php-cgi.exe        FastCGI serving binary (there is no php-fpm on Windows)
php-win.exe
php8.dll           the PHP runtime
php.ini            generated by us (see below)
cacert.pem         CA bundle we add (the official build ships none)
libpq.dll          Postgres client, and the other support DLLs
ext/
  php_pdo_pgsql.dll
  php_pgsql.dll
  php_redis.dll
  ... (37 bundled + the PECL DLLs we add)
```

### Thread safety

We use the non-thread-safe (NTS) x64 build. yerd serves each site through a
FastCGI worker running `php-cgi.exe`, which is single threaded per process, so
NTS is the right choice.

### The FastCGI slot

Unix ships `php` (CLI) and `php-fpm`. Windows has no FPM, since FPM is a Unix-only
SAPI. The equivalent on Windows is `php-cgi.exe`, the FastCGI binary, which is
what nginx or the yerd proxy talks to. It is included in the official build, so
we ship it as-is.

## Extensions

Three groups make up the extension set on Windows:

1. **Built into `php8.dll`.** Roughly 15 of the yerd extensions (bcmath, ctype,
   dom, filter, phar, session, tokenizer, the xml family, zlib, and so on) are
   compiled into the runtime and need no configuration.

2. **Bundled `ext/*.dll`.** The official build ships 37 extension DLLs.
   `repackage-windows.sh` enables every one that appears in `STABLE_EXTENSIONS`
   (24 of them, including curl, gd, intl, mbstring, openssl, sodium, pdo_mysql,
   pdo_pgsql, pgsql, pdo_sqlite, sqlite3, zip, soap, and opcache). The list is
   computed at build time by intersecting the yerd set with what the build
   actually ships, so there is no separate Windows extension list to keep in
   sync.

3. **PECL, added by us.** The official build does not bundle PECL extensions.
   `WINDOWS_PECL` in `config.sh` pins the ones yerd wants (redis, apcu, and the
   igbinary and msgpack serializers) by version. We download the prebuilt NTS x64
   DLL for each, drop it into `ext/`, and enable it. This step is best-effort: if
   a pinned version has no Windows DLL for a given minor and VS toolset, we log a
   warning and continue, because the core bundle is already complete without it.

4. **imagick, handled separately.** imagick is a PECL extension too, but its zip
   is not a single DLL. It ships `php_imagick.dll` plus ImageMagick's own runtime,
   around 160 `CORE_RL_*`, `IM_MOD_RL_*`, and `FILTER_*` DLLs. `php_imagick.dll`
   goes in `ext/`; the runtime DLLs go in the bundle root next to `php.exe`,
   because the Windows loader resolves a loaded DLL's dependencies from the
   executable directory, not from `ext/`. This adds roughly 60 MB to the bundle,
   which is why it has its own `WINDOWS_IMAGICK` version pin rather than riding in
   `WINDOWS_PECL`. Blank the pin to leave it out.

Not bundled: imap, event, opentelemetry, and protobuf. imap was removed from PHP
core in 8.4 and its Windows build is awkward (the c-client dependency); the others
are less common. Any of them can still be added by dropping the PECL NTS x64 DLL
into `ext/` and adding an `extension=` line, which is the normal way to add an
extension to a Windows PHP.

### A note on the redis serializer

The prebuilt Windows redis DLL is not compile-linked against igbinary, so
`Redis::SERIALIZER_IGBINARY` is not defined even though igbinary itself loads
fine. redis, apcu, igbinary, and msgpack all work as standalone extensions. Wiring
igbinary into redis as a serializer would need a custom redis build, which defeats
the point of repackaging, so we do not do it.

## The generated php.ini

`repackage-windows.sh` writes the `php.ini` in the bundle. It sets
`extension_dir = "ext"` and enables the extensions described above. Two details
matter:

- `extension_dir` is relative and that is fine. On Windows PHP resolves a relative
  `extension_dir` against the directory of `php.exe`, so the bundle stays
  relocatable.

- `curl.cainfo` and `openssl.cafile` are a different story. PHP resolves those
  against the current working directory, not against `php.exe`, so a relative
  value breaks under a FastCGI worker whose working directory is the site root. We
  cannot know the final absolute path at package time, so we ship `cacert.pem` in
  the bundle and leave the two settings commented out with a template. The daemon
  must write the absolute extracted path when it installs a version. Without this,
  outbound HTTPS from PHP fails certificate verification.

## Manifest shape

Unix entries in the manifest carry a `cli` object and an `fpm` object, one per
single-file tarball. A Windows entry carries a single `bundle` object pointing at
the directory tarball. `generate-manifest.php` handles both.

## Version and toolset resolution

The filename on windows.php.net encodes the VS toolset the build was compiled
with. PHP switched to VS17 (Visual Studio 2022) at 8.4 and to VS16 (VS2019) at
8.0; 7.x is VC15 (VS2017). So:

| PHP minor      | VS tag |
|----------------|--------|
| 7.4            | vc15   |
| 8.0, 8.1, 8.2, 8.3 | vs16 |
| 8.4, 8.5       | vs17   |

`repackage-windows.sh` maps the minor to the tag and downloads from the current
`releases/` directory, falling back to `releases/archives/` for older patches.

## Channels

Windows builds in both channels. The stable channel covers 8.2 through 8.5 and
the legacy channel covers 7.4, 8.0, and 8.1. Unlike the Unix legacy build, which
needs a stack of source patches to compile EOL PHP with static-php-cli, a legacy
Windows build is just another official download, so there is nothing special to
do. All three legacy versions repackage with the full extension set, pgsql and
the PECL extensions included. The one wrinkle is PHP 7.4, which ships gd as
`php_gd2.dll` instead of `php_gd.dll` (it was renamed in 8.0), so
`repackage-windows.sh` special-cases that one filename.

## Building locally

`build-local.sh` runs the same three steps CI runs (build, verify, package) for
one target on the host:

```bash
# latest patch for the minor, host arch:
scripts/build-local.sh 8.4 windows

# pin an exact patch:
PHP_VERSION=8.4.24 scripts/build-local.sh 8.4 windows
```

The output lands in `./dist`. The verify gate checks that curl has no c-ares, that
an HTTPS fetch works with the bundled CA, that pgsql and the bulk extensions load,
that `php-cgi.exe` reports `cgi-fcgi` and carries the same modules, that the PDO
pgsql and sqlite drivers are present, and that the ZEND_MODULE_API_NO matches what
yerd-php-ext expects.

### Requirements on the build host

The Windows leg needs far less than the static build. It needs `bash`, `curl`, and
a bsdtar (`tar.exe` from System32, which unpacks zip and understands `C:\` paths).
Git for Windows provides bash and curl, and Windows 10 and 11 provide bsdtar, so a
`windows-latest` runner or a normal dev box has everything already. There is no
Visual Studio, no static-php-cli, and no PHP toolchain involved.

## Follow-ups

These are known and intentionally left for later:

- **Daemon wiring in the yerd repo.** The daemon needs to learn the Windows
  contract: extract a directory bundle rather than a single file, run
  `php-cgi.exe` for FastCGI, and set the absolute `curl.cainfo` and
  `openssl.cafile` paths in `php.ini` at install time.

- **A real CI run.** The Windows job is wired into `release-channel.yml` but has
  not yet run on an actual `windows-latest` runner.

- **Source integrity.** We fetch over HTTPS only. windows.php.net publishes
  sha256 sums, so we could verify the downloaded zip against them.

- **PECL coverage.** redis, apcu, and imagick are in. imap, event, opentelemetry,
  and protobuf are not. A brand new minor may also lag on PECL Windows DLLs until
  upstream publishes them, which the best-effort step reports as a warning.
